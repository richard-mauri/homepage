# Homepage architecture contract

Homepage is a small Go standard-library server and same-tab launcher. `main.go` embeds the `static/*` UI and handles configuration, health checks and the optional suite persistence endpoints. `LISTEN_ADDR` defaults to `127.0.0.1:8787` behind a separate Cloudflare tunnel. The private tunnel token, user credentials, logs and local build artifacts must never be committed. `devbuild.sh` runs tests and compiles native Intel/Apple Silicon binaries using Git-private local build counters; `homego.sh` restarts only Homepage and its tunnel when the owner chooses.

## Single twelve-hour Homepage account session
Homepage is the sign-in authority. A personal approved credential creates one 12-hour opaque Homepage session. The browser keeps only its temporary Homepage session ID in Homepage-origin `localStorage`; the approved personal credential is never saved. The Homepage-only cookie is host-only and does not authenticate sister-domain apps. Server-side storage, profile and role checks use the approved-credential digest and server-maintained session/bearer records. Session and handoff records are durably stored in `SUITE_DATA_DIR/auth/homepage-sessions.json` (0600, atomic replacement and file sync). The file stores SHA-256 hashes of opaque Homepage session IDs and app handoff bearers, not raw tokens or approved personal credentials. Each load preserves the original absolute expiration, and a restart must not extend it. The service refuses to start if existing session state cannot be recovered; failures to persist login, handoff, renewal or sign-out mutations fail rather than reporting false success. The storage directory must be a persistent, writable volume and should be protected and backed up appropriately. Roles and per-user storage authorization remain server-enforced.

NewsGo and MauriStocks require a transferable bearer for secure cross-origin calls, but **not an independent login**: on a signed-in launcher click, `POST /api/handoff/token` issues a bearer bound to the active Homepage session. Its expiration is capped by that session's original 12-hour expiration. A bearer cannot remain valid after the parent session expires or is signed out, and its originating credential is revalidated at each request. Every app handoff created under the same parent login is invalidated on `DELETE /api/session`, including bearers previously rotated through the legacy renewal endpoint. The old `-handoff-minutes` server flag is removed; the session lifetime is fixed at 12 hours. The legacy `/api/handoff/renew` endpoint is retained for backward compatibility with older app versions, but cannot extend a bearer beyond its parent session expiration. For backward compatibility during NewsGo migration, the older NewsGo flow still offers explicit renewal of an **unexpired** parent login: `POST /api/handoff/extend-session` accepts only a valid parent-bound NewsGo bearer from the exact NewsGo origin and atomically extends its Homepage parent expiry to twelve hours from the renewal request while rotating the NewsGo handoff. It does not accept credential-only bearers, expired or revoked sessions, cookies, or untrusted origins. The rotated bearer and new expiry are returned to NewsGo without a navigation or a personal credential prompt. The authoritative UI for manual renewal is now Homepage: same-origin POST `/api/session/renew` requires a valid opaque `Session` header and approved credential digest, updates the parent expiry to twelve hours from the request, and extends only already-live child handoffs from that parent. It never revives expired handoffs or sessions. The `/suite-admin` Manage Tokens page places its countdown and renewal action in the Current session panel beside Disconnect for every signed-in user, not only administrators; the Homepage header has no redundant Sign out control. Manage tokens is visible to any authenticated user while the Approved users section remains admin-only. Disconnect sends the opaque Session header when available, revokes its parent-linked handoffs and clears the Homepage-origin localStorage session and sessionStorage handoff cache only after server confirmation. Successful renewal also refreshes the host-only HttpOnly session cookie's 12-hour Max-Age, preventing the Manage Tokens page from losing cookie authentication at the former deadline. Other handoffs retain their original expiration; sign-out invalidates all parent-linked handoffs. The Homepage browser revalidates its stored opaque session ID after return, even if its cached expiration predates a renewal. Legacy `/api/handoff/renew` remains capped by the parent expiry.

App handoff bearers are transmitted only in destination URL fragments, never URL query strings. The destination app removes the fragment from browser history and stores the bearer in its own origin's `sessionStorage`. Server validation is authoritative; the cached token is not a separate sign-in. Only trusted app origins may use the bearer-protected profile and revisioned per-user account storage APIs.

## Same-tab launcher and browser-only access
Homepage cards navigate to their configured HTTPS app destinations in the current browser tab. When the Homepage browser is signed out, the NewsGo and MauriStocks links explicitly navigate with `#suite_mode=local`, instructing the app to delete its cached bearer and enter browser-only mode without changing local settings. A handoff issuance failure also uses `#suite_mode=local`, not an old token. When signed in, a successful handoff includes `#suite_token=...`. The destination apps keep a valid bearer across ordinary reloads but must revalidate it with Homepage's API, which returns unauthorized after sign-out or expiry. Each app provides a native Back to Homepage link. No native blocking sign-in alerts, named tabs, new tabs or forced focus.

The changed launcher and auth contracts require coordinated NewsGo and MauriStocks client updates and Mac/Safari verification. Do not infer browser acceptance from CI alone.

## Authentication diagnostics

Homepage's optional `-trace` flag enables server-side auth HTTP result tracing and a same-origin `POST /api/trace` receiver for the browser's navigation/auth UI decisions. `/api/config` advertises only the trace-mode boolean. Every browser event is validated against fixed event and phase allowlists and a 16-character random page correlation ID. Logs go to the standard logger, which `homego.sh` redirects to `homepage.log`. Tracing never records raw cookies, approved credentials, session IDs, handoff tokens, usernames or private preferences. Session lookup outcomes are reported as a small fixed set (missing, expired, credential revoked, valid), and trace mode is off by default.

## SailingGo account preferences (Issue #26)

SailingGo at `https://weather.themauris.org` is a third trusted application origin for Homepage's bearer-protected `/api/session/profile` and revisioned `/api/storage/sailing` endpoints. The signed-in SailingGo card receives the same fragment-only `#suite_token` handoff as Stocks and NewsGo; a signed-out visit receives `#suite_mode=local`. The approved credential and host-only Homepage cookie never travel to SailingGo. Each storage record is authorized by the server-verified Homepage user, not by client-supplied user IDs. Existing NewsGo and Stocks namespaces remain unchanged. This change does not add a direct-visit `/launch/sailing` bridge; initial account access requires launching from signed-in Homepage.

## Direct-visit suite session recovery (Issue #24)

The strict no-store, CSP-protected `/launch/newsgo`, `/launch/stocks` and `/launch/sailing` GET routes serve the same static recovery bridge on Homepage's origin, with only fixed destinations and no GET credential issuance. Bridge JavaScript uses the existing same-origin `POST /api/handoff/token`, a retained opaque Homepage session ID or host-only HttpOnly cookie, and fragment-only return of a parent-bound child bearer. Authoritative 401 returns `#suite_mode=local`; storage/network errors do not imply sign-out. Browser session recovery never creates, revives, or renews an expired parent. Each consuming app independently implements navigation to its corresponding route when no bearer is present; a direct visit to an unmodified app will not trigger recovery. SailingGo's namespace and trusted weather origin added by Issue #26 remain unchanged. This PR is coordinated with NewsGo #80, existing merged MauriStocks #12 and a SailingGo direct-visit companion.

## Activity collector (Issue #28, draft implementation)

The Homepage-only API candidate is isolated from session renewal and credential registration. `POST /api/admin/activity/ingest` uses one fixed service identity, a separate server-only bearer secret per service, timestamp skew validation, bounded strict JSON and per-service nonce replay rejection; browser `Origin` requests are refused. `GET /api/admin/activity` revalidates the Homepage session and requires the current server-side `admin` role. Neither endpoint grants or extends an account login.

The collector stores at most one current aggregate report for each of the five known services. It marks missing reports `unknown` and reports older than 150 seconds `stale`; a successful cold startup does not restore in-memory active-state from disk. A bounded per-service, per-UTC-hour sample series is durably written to `SUITE_DATA_DIR/activity/hourly.json`, kept separate from `auth/homepage-sessions.json`. The atomic writer restricts permissions, writes/syncs a temporary file, renames and syncs its directory. If the history cannot be loaded, the collector rejects future writes rather than replacing corrupt history; the rest of Homepage continues operating. No IDs or credentials go in history. Hourly sample counts and peaks **cannot** establish hourly unique visitors or safe restart conditions.

This branch is not a full monitoring system: no client reporters, in-flight handler instrumentation, dashboard, or safe-restart logic exist. The API route is registered only when suite persistence is enabled, and the service bearer secrets remain optional until instrumented. Sister application processes and tunnels remain entirely independent.

### Homepage-origin browser presence (draft)

`POST /api/activity/ping` accepts only strictly same-origin JSON with a bounded, lowercase-hex, 128-bit browser-tab nonce; no bearer, login, or cookie is required, and the server revalidates a present Homepage cookie to classify the observation as authenticated. A bounded in-memory map deduplicates reports, prunes at 60 minutes, throttles a given identifier to one accepted report per 15 seconds, and marks missing or aged presence stale rather than incorrectly fresh. Activity is not a session renewal and cannot create a session. Browser heartbeats are visibility-aware and separate passive presence from user interaction. This records Homepage only, not cross-app visitors; spoofed same-origin-looking nonbrowser requests remain possible, so the indicator is advisory.

Homepage hourly aggregates are sampled approximately once per minute under active traffic. Server-to-server aggregated samples retain their independent ingestion path. To limit SSD wear, history's first accepted sample flushes to disk; subsequent changes flush on a later ingestion after five minutes rather than synchronously on every report. Unflushed aggregates are lost on abnormal shutdown; this is an intentional best-effort telemetry tradeoff, not authorization state. Monitoring errors do not affect Homepage logins or application function.

### Admin activity presentation (draft)

`static/suite-admin.html` embeds an admin-only **Session activity** view without changes to the existing token-management endpoints. When the currently validated Homepage session has role `admin`, the browser reads `GET /api/admin/activity` with `Authorization: Session ...`, renders status labels and per-service metrics, and refreshes while the tab is visible. The server endpoint independently revalidates session and role on every request, so the hidden client panel is only a presentation convenience, not access control. Invalid / missing observations remain unknown, never interpreted as zero. Hourly bars are computed from `active2Sum / samples` by UTC hour-of-day within a selected 7- or 30-day window. No behavior change to the 12-hour session timer, Renew, Disconnect, or approved-token management; no restart control is exposed.
