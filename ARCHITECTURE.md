# Homepage architecture contract

Homepage is a small Go standard-library server. `main.go` is the HTTP composition root: it embeds `static/*`, configures `/api/config`, `/healthz`, static assets and the homepage, and exposes a simple `-version` CLI flag. Keep this small; extract packages only when justified by actual complexity.

`static/index.html`, `static/styles.css`, `static/app.js` and `static/favicon.svg` own browser markup, styling, client interactions and icon. No browser build pipeline is required. The frontend receives link metadata from `/api/config`. App cards contain absolute HTTPS links and open external destinations; they do not proxy services or perform remote API operations. Default destinations are weather, stocks, newsgo and scrapergo subdomains of `themauris.org`.

`LISTEN_ADDR` defaults to `127.0.0.1:8787` and is consumed by the external Cloudflare tunnel. The tunnel is a distinct process. Its private token resides under `.cloudflared/token`, which must never be committed. Avoid broad network binds, admin endpoints, untrusted redirects or secrets in responses. Environment URL overrides require an operator-controlled environment; do not accept arbitrary client-provided URL settings.

`devbuild.sh` runs `go test -count=1 ./...`, reserves the next build number at Git's private `homepage-build-counter` path, compiles standalone Intel and Apple Silicon binaries and writes `dist/SHA256SUMS`. `appVersion` and `appBuild` are separate: semantic version changes only by owner decision; the build label is injected at link time. The counter is per-checkout, not a global sequence across machines. `homego.sh` validates the stamped binary and restarts only Homepage and its matching tunnel.

Changes must preserve the route contract, accessible responsive UI, external link safety, machine-specific process isolation and credentials exclusion. Add tests around new behavior; no claim that compiling validates real Safari/Cloudflare behavior.

## One-hour app handoff (candidate)
Homepage issues a random 256-bit bearer (default one hour, configurable at server startup with `-handoff-minutes` from 1 to 1440) via authenticated same-origin `POST /api/handoff/token`, accepting an existing Homepage session or the approved credential during a fresh Homepage sign-in. It stores only the token digest and the approved-credential digest in memory and checks credential revocation and role at each request. The launcher adds `#suite_token=...` to NewsGo and MauriStocks links (no URL query or server log exposure). Apps remove the fragment immediately and keep it in tab `sessionStorage`, use it in `Authorization: Bearer` for Homepage's allowlisted profile and revisioned storage APIs. Homepage retains a host-only login cookie for its own sign-in UI and handoff issuance. NewsGo and MauriStocks must use the one-hour bearer for profile and storage access; cross-app cookie fallback is rejected server-side. The cookie is never scoped to sibling subdomains. Server restarts invalidate handoff tokens; expired/revoked tokens require returning to Homepage. Never treat browser UI roles as admin authority.

## Token renewal and launch timing
Homepage generates a fresh handoff when a user clicks a NewsGo or MauriStocks launcher card; launch navigates in the same Safari tab after issuance to avoid asynchronous popup blocking. Applications can rotate a still-valid token with `POST /api/handoff/renew`, authenticated solely by the current bearer, with CORS allowed only for the two app origins. The endpoint issues a fresh token with the configured lifetime, invalidates the old bearer, and rejects expired credentials. `/api/session/profile` includes `expiresAt` for bearer requests so applications can display an accurate countdown. Renew is user-triggered, not automatic.

## Homepage login restoration across application navigation
Homepage's own twelve-hour login is represented by a random session ID independently of the short-lived app handoff token. POST and GET /api/session return `sessionToken` and `expiresAt` only to the same-origin Homepage browser, which retains the transient ID in Homepage-origin localStorage and explicitly sends `Authorization: Session <id>` for future Homepage status, handoff issuance, and logout. The approved personal token is never stored by the browser. Existing Homepage-only cookie authentication remains for the standalone suite-admin screen; the Homepage launcher does not rely on that cookie to restore login. A validated cookie status can bootstrap the explicit session ID. The server still keeps twelve-hour sessions in memory, so a Homepage process restart invalidates them. No app accepts this Homepage session ID; each app uses its own short-lived handoff bearer.

## Reusable application tabs (candidate)
Homepage uses a deterministic named browsing context based on each configured HTTPS destination's hostname. A direct click opens/focuses that named tab synchronously before asynchronous NewsGo/MauriStocks account-token issuance; the pre-opened handle receives the final URL with a fresh token fragment only if sign-in and issuance succeed. Signed-out visitors open the same apps without a token; Homepage stays in its own tab. The normal launch removes the opener reference while the newly opened about:blank tab is still same-origin; the native anchor retains noopener/noreferrer for popup-blocked or modified-click fallback. Homepage also retains an in-memory WindowProxy per app and focuses that existing handle without navigating on repeat clicks. The handle map survives while the original Homepage document remains loaded; reloads lose it. Safari may report a cross-origin isolated window as closed or block focusing, so tab reuse remains best-effort. Manually opened/unrelated tabs cannot be discovered by this site, and browser settings or COOP may require a new tab. No tokens appear in persistent card hrefs and none are sent to non-suite apps. Test iPhone Safari, macOS Safari, signed-in and signed-out paths, repeated app cards, expiration, closed tabs and external links before merging.

### Safari tab activation limitation
A retained app WindowProxy and `focus()` cannot guarantee Safari switches to a background tab. When a repeat click finds an open app handle, Homepage requests focus but keeps the app's document untouched. It also displays an accessible, styled message indicating the application is already open and instructing the user to select its Safari tab. The message is not evidence that focus succeeded. A web page cannot reliably enumerate and activate arbitrary Safari tabs. This behavior deliberately prioritizes app state preservation over forced navigation and is subject to owner Safari acceptance.
